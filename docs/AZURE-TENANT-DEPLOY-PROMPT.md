# Deploy Market Pulse in Your Azure Tenant

Share this document with the person deploying the app. They can paste the prompt below into their coding assistant after opening a terminal or VS Code workspace on a machine where they can sign in to their own Azure tenant.

## Copy-ready prompt

```text
Deploy this application into my Azure subscription, not the original owner's subscription.

GitHub repository: https://github.com/harsh-cloudforce/Linkedin-mcp

Please work through the deployment with me, not just give me a generic checklist:

1. Clone the repository if it is not already open, then inspect README.md, azure/CLOUD-SHELL-DEPLOY.md, docs/AZURE-GITHUB-DEPLOY.md, and the scripts in scripts/ before running deployment commands.
2. Check that I can access the repository and that Azure CLI is installed. Ask me to sign in with `az login`, select my subscription, and confirm the subscription ID and tenant shown by `az account show`. Do not continue if the selected subscription is not mine.
3. Before creating Azure resources, show me the resource names, region, and expected billable services and get my confirmation. Use a dedicated resource group. ACR, storage account, and app/environment names must be available and unique where Azure requires it. Do not reuse names or resource IDs from the original owner's tenant.
4. Follow the repository's Cloud Shell deployment instructions to bootstrap the LinkedIn scroller: create the resource group, ACR, Container Apps environment, scroller app, and its MCP bearer-token secret. Build from this repository's `scroller/` source. Use the same resource group, ACR, and Container Apps environment for both apps. If using Cloud Shell, help me make the source available there without asking me to put Azure credentials or deployment secrets in GitHub.
5. Configure Azure Files persistence for the scroller profiles and webapp data using the existing `scripts/ensure-scroller-storage.ps1` and `scripts/ensure-webapp-storage.ps1` helpers as appropriate. Set `SKIP_POSTGRES=1` for the webapp deployment unless I explicitly choose and approve PostgreSQL charges.
6. Before running the PowerShell deployment scripts, help me create the ignored local file `azure/.env` with my resource group, region, ACR name, storage account name, scroller app name, scroller FQDN, and the scroller MCP bearer token. The token must stay in this local ignored file / Azure secret store. Do not print it, put it in source control, or ask me to paste it into this chat. Confirm `azure/.env` is ignored by Git.
7. From the repository root, deploy/update both apps with:
   `./scripts/deploy-containerapp.ps1`
   `./scripts/deploy-webapp.ps1`
   Use PowerShell syntax appropriate to my operating system. Do not run a deploy script until its required Azure resources exist.
8. Verify both apps' `/healthz` endpoints, report the dashboard, login, and scroller MCP URLs, and help me sign in with the admin credentials generated by the webapp script. Keep generated credentials in my local ignored `azure/.env`; don't echo them into this chat. Explain how to generate the webapp integration API key from Settings.
9. If a command fails, diagnose the actual error and continue from the current state. Avoid deleting resources or changing unrelated files. Do not commit or push secrets.

Important: the current `.github/workflows/deploy.yml` contains the original owner's Azure resource names and deploys only the scroller. Do not run or enable that workflow for my tenant. A later GitHub Actions setup would need tenant-specific resource values and OIDC secrets/permissions.

Stop and ask me before any resource deletion, unexpected paid service, permission escalation, or change outside this deployment. Never ask me to send passwords, tokens, client secrets, or other credentials through chat; have me enter them directly into the appropriate local file, terminal prompt, or Azure Portal field.
```

## Before sending

- Give your colleague access to the GitHub repository. They need to be able to clone it; Azure access is separate and must be to their own subscription.
- The colleague should use an Azure subscription with permission to create the resources listed above. Azure charges will be billed to that subscription.
- Do not send your `azure/.env`, bearer token, integration key, admin password, or Azure credentials.

The repository's detailed deployment references are [CLOUD-SHELL-DEPLOY.md](../azure/CLOUD-SHELL-DEPLOY.md), [AZURE-GITHUB-DEPLOY.md](AZURE-GITHUB-DEPLOY.md), and the root [README.md](../README.md).
